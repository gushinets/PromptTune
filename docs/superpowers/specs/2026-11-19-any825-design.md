# ANY-825: monthly quota and verified email bonus

Status: approved by the user on 2026-11-19; SMTP credentials will be supplied at deployment. Product requirements are settled in ANY-825.

## Sources and intent

Implement https://linear.app/paveldik/issue/ANY-825 using its updated acceptance criteria. Read both original attachments from Downloads: `Prompt_Optimizer_Email_50_Improvements.html` and `PromptOptimizer — механика бесплатных.md`. The ticket overrides their older behavior (immediate unverified bonus, full UI blocking, test balance of one).

Give each installation 50 successful improvements per calendar month anchored to its installation date. A verified email earns exactly one additional package of 50, globally per normalized email. Preserve results and library access when quota is exhausted.

## Current code

- `backend/app/services/rate_limiter.py` uses Redis daily/minute counters and merges installations sharing an IP. It reserves before generation and refunds failures/cancellation.
- `PromptService` records installations/results in PostgreSQL. There is no email delivery or verification service.
- `/v1/limits`, improve responses, background messages and popup all expose daily counters. Popup and side panel share `App.tsx`; exhausted UI currently offers a coming-soon upgrade.
- Current branch is `ANY-825`; working tree was clean at inspection.

## Approaches

1. Recommended: durable PostgreSQL quota, email proof through a short-lived code entered in the extension, SMTP delivery. Fits the existing database and popup; requires mail configuration but no hosted verification page.
2. Email verification link and hosted confirmation page. Similar persistence, but requires public URL configuration and synchronization back into the extension.
3. Durable Redis quota. Fewer database changes, but requires explicit persistence/backups and a permanent deduplication ledger. PostgreSQL already supplies durable transactions and uniqueness constraints.

Proposed choice: approach 1. No paid plan, extra bonus renewals, external account system, or n8n quota redesign.

## Quota persistence and lifecycle

Add an Alembic migration for an installation quota, email claims, challenges and generation reservations. Store balance, original anchor date, period start/end, email, verification and bonus state durably. Keep the global normalized-email claim unique permanently; resetting the month must never delete it.

Use the server-side Installation.created_at as the anchor for existing installations and the first server registration for new installations. Client-provided dates cannot move the quota boundary. Use the explicitly permitted Moscow timezone, midnight on the anchor day of each month, clamping to the last day in shorter months while preserving the original day for subsequent months. First refresh is in the following month, not the next day. Lazy refresh on quota access skips elapsed months and replaces the balance with 50, discarding all previous unused base/bonus units.

Migration choice by the implementer: existing installations receive a fresh balance of 50 on their first access after migration; historical daily usage is not retroactively deducted. Their next renewal still follows the original installation anniversary in the current monthly period. This avoids penalizing users for usage under the previous daily allowance.

Do not merge quota by IP: unrelated users behind NAT must have separate monthly balances. IP can still limit request/code abuse. Reinstallation may create a new installation, but cannot produce a second bonus for an email in the claim ledger. After verifying an already claimed email on a new installation, record that its bonus is unavailable without issuing credit. Never disclose or attach another installation's balance from an unverified email.

## Concurrent improvement and cancellation

Reserve quota atomically in a short transaction before starting LLM work; never hold a transaction/row lock over network generation. Persist a unique reservation with its period and expiry. Finalize once on success; failures/cancellation release it once. Expired reservations recover after worker crashes; late results cannot finalize an expired/reclaimed reservation or charge a new monthly period. All quota and bonus writes serialize on the installation row and global email uniqueness constraint. The success response contains authoritative quota following finalization. Existing disconnect cleanup must remain functional.

No daily restriction. Retain a separate configurable minute abuse throttle if appropriate, distinguishing it from monthly exhaustion in API errors and UI; a minute 429 must not zero out the monthly balance.

## Email verification

Add endpoints under `/v1` to request a verification challenge and confirm its code, with installation identity obtained through the same background/API path as limits. Validate email on the server and normalize whitespace/case consistently. One pending email challenge per installation. Proposed defaults: a cryptographically random six-digit code, 10 minute expiry, maximum five guesses, 60 second resend cooldown and bounded request rates per installation/IP/email. Only store a keyed code digest; do not return/log codes or include them in analytics. A resend invalidates the prior challenge.

Deliver through authenticated SMTP with configurable sender, host, port, user/password and TLS. No credentials in source, no fake delivery success, no production shortcut to bypass confirmation. If SMTP is missing/fails, report a recoverable error and issue no bonus. Include environment template and deployment documentation. Actual production mail credentials must be supplied by the operator; local automated tests use a fake mail sender.

On successful proof, consume the challenge and insert the permanent email claim in the same transaction as incrementing quota by 50 and setting verified/bonus state. Unique conflict means no new credit. Repeated successful confirmation returns current state without another increment. One bonus per installation as well as per email: changing addresses cannot repeatedly top up the same installation. Confirmation and monthly refresh run under the same quota lock, so stale balance writes cannot erase or duplicate a bonus.
